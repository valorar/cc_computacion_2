Proyecto: una aplicación que resuelve un problema real

Reúnes todo el curso en un producto: eliges un problema, lo planificas, construyes la aplicación por partes, la pruebas y entregas las evidencias. Tú decides qué construir.

  • 8–10 sesiones
  • Prácticas de la evaluación
  • 1 evaluación Moodle
  • Trabajo en el aula

Al terminar podrás:

  • elegir un problema real que se resuelva con una aplicación sencilla;
  • escribir una ficha con objetivos, usuarios, entradas, salidas y plan de trabajo;
  • construir la aplicación por partes, probando cada una antes de integrarla;
  • documentar el proyecto y presentar evidencias del proceso y del resultado.

Pregunta guía
Piensa en una tarea repetitiva que alguien de tu entorno hace cada semana con papel, una hoja de cálculo o la memoria. ¿Podrías escribir el programa que se la ahorre?
01 / ELEGIR

Elegir un problema que de verdad importe

Un buen proyecto no es el más impresionante, sino el que alguien usaría. Criterios: el problema es real y cercano (biblioteca del aula, liga de recreo, gastos de un viaje); tiene usuarios concretos; los datos de entrada y salida están claros; y puedes terminarlo en las sesiones previstas. Evita los clásicos: «una app con cuentas», «un juego con gráficos», «el programa que lo hace todo».

Las mismas fases sirven para una interfaz web o una app móvil sencilla (p. ej. App Inventor); este curso entrega una aplicación de consola en Python, pero el proceso es idéntico.

Idea claveUn problema pequeño resuelto del todo vale más que un problema grande a medias. El alcance se decide al principio y no se mueve sin motivo.
02 / PLAN

Del problema a la ficha del proyecto

Antes de escribir código, escribes una ficha que convierte la idea en algo comprobable. Es la disciplina del tema 15 aplicada a un producto entero. Un ejemplo para un registro de préstamos de libros:

  • Objetivo: saber qué libros están prestados, a quién y desde cuándo.
  • Usuarios: la persona encargada de la biblioteca del aula.
  • Entrada: título, persona y fecha; salida: préstamos activos y avisos de devolución.
  • Datos: fichero JSON (tema 13) y clase Préstamo (tema 14).
  • Plan: sesiones 1–2 ficha y datos; 3–4 núcleo; 5–6 menú; 7–8 pruebas y documentación.

La ficha lista también las funciones esperadas: cada una con su nombre, qué recibe y qué devuelve. Si una función no cabe en una frase, el paso es demasiado grande: divídelo. El plan de sesiones protege el final: deja las últimas sesiones para probar y documentar, no para terminar a toda prisa.

03 / PARTES

Construir por partes: lógica e interfaz

La construcción empieza por el núcleo: funciones que procesan datos sin menús, fáciles de probar porque no piden nada al usuario. Después llega la interfaz: el menú que pregunta y muestra. Separar ambas capas es la decisión de diseño más rentable del curso.

def prestamos_activos(prestamos):
    """Préstamos aún no devueltos.

    Sin la clave 'devuelto', el préstamo se trata como activo:
    un dato ausente no significa devuelto."""
    return [p for p in prestamos if not p.get("devuelto", False)]

# Pruebas: [] -> [] · 3 préstamos con 1 devuelto -> 2
#          sin clave 'devuelto' -> se cuenta como activo
def main():
    """Bucle del menú: pedir opción, actuar y repetir hasta salir."""
    print("1. Nuevo préstamo  2. Devolver  3. Listar  0. Salir")

if __name__ == "__main__":
    main()      # al importar el módulo, este bloque no se ejecuta

if __name__ == "__main__" permite ejecutar el archivo como programa o importarlo desde una batería de pruebas sin que el menú salte solo. Cuando el núcleo responde a la ficha, se conecta el menú y el programa se vuelve una aplicación.

04 / PRUEBAS

Probar contra la ficha, no contra la suerte

Cada requisito de la ficha tiene al menos una prueba, escrita junto a la función que lo cumple, y la batería incluye siempre el caso normal, los límites y los datos inválidos:

def primera_mayuscula(palabra):
    """Convierte la inicial en mayúscula sin tocar el resto."""
    return palabra[:1].upper() + palabra[1:]

# Batería mínima: normal, límite y error
assert primera_mayuscula("hola") == "Hola"    # caso normal
assert primera_mayuscula("HOLA") == "HOLA"    # no rompe mayúsculas
assert primera_mayuscula("") == ""            # vacío: no debe explotar

La prueba de regresión es el ritual de cada sesión: tras cualquier cambio se ejecuta la batería entera y el arreglo es pequeño. Al final se prueba la aplicación completa contra la ficha, incluido el arranque con el fichero vacío o dañado.

Idea claveNo hay «probar al final»: hay una batería que crece con cada función. La aplicación está terminada cuando la batería pasa y la ficha se cumple.
05 / ENTREGA

Documentar y presentar evidencias

Un programa sin documentación es un tesoro sin mapa. El proyecto se entrega con un README breve que responde a cuatro preguntas: qué hace, cómo se ejecuta, qué ficheros usa y cuáles son sus funciones principales; cada función lleva su docstring y el código sigue las prácticas del tema 15.

Las evidencias demuestran el proceso, no solo el resultado: ficha inicial, batería de pruebas con resultados, capturas o demostración en vivo y autoevaluación contra la rúbrica. Presentar el proyecto en dos minutos —problema, solución, demostración— cierra el curso como empezó: explicando lo construido.

06 / SALIDA

Lo esencial

  1. Elige un problema real, pequeño y con usuarios concretos; el alcance se fija en la ficha.
  2. La ficha define objetivo, usuarios, entradas, salidas, funciones esperadas y plan de sesiones.
  3. Construye primero el núcleo de funciones probables y después la interfaz.
  4. La batería crece con cada función (normal, límites, inválidos) y se reejecuta tras cada cambio.
  5. Entrega README, docstrings, batería con resultados y demostración: evidencias del proceso.
