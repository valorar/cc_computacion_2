Tema 15 · Bloque D · 3.ª evaluación

Depurar, probar y mejorar

Que un programa funcione no es un misterio: es leer errores con método, probar con casos pensados y mejorar el código por partes pequeñas.

  • 5–6 sesiones
  • Prácticas de la evaluación
  • 1 evaluación Moodle
  • Trabajo en el aula

Al terminar podrás:

  • clasificar un error como de sintaxis, ejecución o lógica y localizarlo en el traceback;
  • usar trazas y un depurador paso a paso para observar qué ocurre dentro del programa;
  • escribir casos de prueba que cubren lo normal, los límites y los datos inválidos;
  • planificar la secuencia de tareas y mejorar el código con pequeños cambios probados.

Pregunta guía
Un programa tuyo da un resultado equivocado sin ningún mensaje de error. ¿Por dónde empiezas: por el código, por los datos de entrada o por lo que esperabas que hiciera?
01 / ERRORES

Tres familias de errores

El error de sintaxis incumple las reglas del lenguaje (dos puntos olvidados, comillas sin cerrar) y Python se niega a ejecutar. El error de ejecución aparece al correr con una entrada concreta: dividir entre cero, una lista vacía, un archivo que no existe. El error de lógica es el traicionero: el programa corre sin quejarse y devuelve algo incorrecto.

def suma_hasta(n):
    """Suma 1 + 2 + ... + n."""
    total = 0
    for i in range(1, n):      # error lógico: el propio n queda fuera
        total += i
    return total

# Pruebas: suma_hasta(3)->3 (esperado 6) · suma_hasta(5)->10 (esperado 15)
# Sin excepciones: el fallo solo se ve al comparar con lo esperado.
Idea claveLa sintaxis la detecta Python al leer, la ejecución al correr y la lógica solo al comparar el resultado con lo esperado: por eso necesitas casos de prueba.
02 / RASTRO

Leer el rastro: tracebacks y depurador

Ante un error de ejecución, Python imprime un traceback. La última línea dice el tipo de error y su mensaje; las superiores, el camino de llamadas que llevó hasta él.

Traceback (most recent call last):
  File "carrito.py", line 12, in <module>
    total += articulos[2]
IndexError: list index out of range

Tres datos: archivo (carrito.py), línea (12) y tipo con mensaje (IndexError: pediste la posición 2 y la lista no llega). Para la lógica no hay traceback, y ahí entran las herramientas de observación: print() provisionales para ver valores intermedios (luego los retiras) y, mejor, el depurador de IDLE, Thonny o Visual Studio Code: punto de interrupción, paso a paso e inspección de variables.

03 / PRUEBAS

Casos de prueba que se ejecutan solos

Probar «a ojo» no sirve: al cambiar el código tendrás que acordarte de todo. Un caso de prueba declara una entrada y su salida esperada, y una buena batería cubre tres categorías: caso normal, límites (vacío, cero, primero, último) y datos inválidos.

def ahorro(mensual, meses):
    """Dinero ahorrado; None si los datos no tienen sentido."""
    if mensual <= 0 or meses <= 0:
        return None
    return mensual * meses

# Batería: caso normal, límites y error
assert ahorro(50, 12) == 600       # caso normal
assert ahorro(1, 1) == 1           # mínimo válido
assert ahorro(50, 0) is None       # límite no válido
assert ahorro(0, 12) is None       # cero sin sentido
assert ahorro(-5, 3) is None       # fuera de dominio

Un assert que falla detiene el programa con AssertionError: eso quieres en desarrollo, un aviso inmediato. Tras cada cambio reejecutas la batería entera, y si algo se rompe lo sabes al segundo. Herramientas como doctest y unittest aparecen en las prácticas.

04 / CALIDAD

Código que se lee y se mantiene

Se programa una vez y se lee muchas; quien más lee tu código eres tú, semanas después. Un código claro se depura solo. La diferencia no es cosmética:

Confuso

def f(n):
    r = []
    for i in n:
        if i not in r:
            r.append(i)
    return r

Claro

def sin_duplicados(elementos):
    """Devuelve la lista sin repetidos, conservando el orden."""
    resultado = []
    for elemento in elementos:
        if elemento not in resultado:
            resultado.append(elemento)
    return resultado

# Pruebas: [1, 2, 1, 3, 2]->[1, 2, 3] · []->[] · [7]->[7]

Nombres que dicen qué hace la función, un docstring con propósito y casos, funciones largas divididas en pasos con nombre, código muerto retirado: hábitos baratos que convierten «adivinar qué quería decir» en «leer y entender». Un conjunto eliminaría duplicados, pero aquí el orden importa y por eso el bucle es la herramienta adecuada.

05 / PLAN

Planificar antes de teclear

Programar sin plan convierte cada tarea en una maraña. El método de las tareas en secuencia: divide el problema en pasos pequeños (entrada, cálculo, salida), ordénalos por dependencias —no muestras resultados antes de calcularlos— y programa uno cada vez, probándolo antes de seguir. Ante cada paso: ¿qué recibe?, ¿qué devuelve?, ¿qué puede fallar?

  1. Divide: escribe los pasos que resolverían el problema a mano.
  2. Ordena según dependencias, del más simple al más complejo.
  3. Programa un paso, pruébalo con sus casos y solo entonces sigue.
  4. Mejora por cambios pequeños y reejecuta la batería tras cada uno.

Ese ciclo —cambio pequeño, prueba, observar, adaptar— mantiene vivo el software cuando cambian los requisitos: no es fracaso, es versión nueva. Guardar versiones con git permite retroceder sin miedo cuando un cambio no funciona.

06 / SALIDA

Lo esencial

  1. Errores de sintaxis, ejecución y lógica: los dos primeros los delata Python, el último solo tus pruebas.
  2. El traceback se lee por tipo y mensaje finales y localiza archivo y línea; el depurador observa variables paso a paso.
  3. Un caso de prueba declara entrada y salida esperada; una buena batería cubre lo normal, los límites y lo inválido.
  4. Un assert que falla detiene el programa: úsalo en desarrollo y reejecuta la batería tras cada cambio.
  5. Nombres claros, docstrings y pasos pequeños hacen el código legible; planifica antes de teclear.
